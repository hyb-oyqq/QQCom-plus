# 监视区刷新性能测试

两种测法，用途不同：

| 方式 | 测什么 | 何时用 |
| --- | --- | --- |
| **A. 基准程序**（`tests/perf`） | 刷新周期的净工作耗时，可重复、可 A/B | 改动了面板/模型/视图后回归 |
| **B. 真实端点灌数据**（`tests/performance_test.py`） | 真实串口/TCP 端到端观感 | M6 压测、真机长稳 |

---

## A. 基准程序（推荐）

直接编译真实的 `MainWindow` + `TrafficPanel`，按"每 16 ms 一批、每批 N 条"灌数据，
测每个刷新周期（追加 → 入模 → 滚底 → 重绘）的耗时。**测的就是出货代码**，
不是用假模型搭的近似复现——卡顿来自面板与视图的协作方式，假模型测不到同一个瓶颈。

### 构建

```powershell

call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"
mkdir build\perf ; cd build\perf
C:\MyProgram\Qt\6.10.1\msvc2022_64\bin\qmake.exe -o Makefile ..\..\tests\perf\traffic_perf.pro `
    -spec win32-msvc "CONFIG+=release" "CONFIG-=debug"
nmake release
```

### 运行

```powershell

.\release\easyDebug_traffic_perf.exe 4096 20 200 0 0
.\release\easyDebug_traffic_perf.exe 128 20 200 0 128000   # 附带投影成本梯度
```

窗口会真实显示（字体度量要跟实际一致），跑完自动退出。

### 判读

主判据只有一条：**"净工作"必须稳定小于 16 ms**（一帧的预算）。
超过它就意味着 GUI 线程追不上消息节奏，队列越积越多，表现为卡顿、发木。

```
刷新周期（追加 → 入模 → 滚底 → 重绘）
  合计   mean    33.06 ms   p50    32.96   p95    34.48   max     36.09 ms
  净工作 mean     7.02 ms   （已扣除每拍刻意等待攒批的 26.0 ms）
  超过 100ms（肉眼可见卡顿）的周期 0 / 200
  帧率 净工作折合 142.4 fps   最差一拍  27.7 fps
```

- **净工作 = 合计 − 每拍等待**。这笔"等待"里其实**包含了插入本身**（攒批定时器
  就是在 processEvents 里触发的），所以它是个"差值"，把一个快得多的插入实现
  算成"等待变短、净工作变大"。**改插入路径时不要只看净工作，要连着"合计"一起看**：
  编辑块优化那次净工作从 4.5 涨到 7.0 ms，而合计从 64.4 降到 33.1 ms、
  落盘延迟从 60 ms 降到 26 ms——真实情况是快了约一倍。
  净工作适合当"帧预算还够不够"的绝对参考，不适合做两个差异很大的实现的 A/B。
- **超过 100ms 的周期**：长尾。用户感知到的正是这个数，它必须是 0。
- **拖动窗口**：跟随开启 + 历史就位下连续改尺寸 ±350px 的同步重绘耗时（本机 mean 15.3 ms）。

### 投影基准（第 5 个参数）

监视区是模型缓冲的**投影**：显示设置、编码格式、过滤条件变化都要重画已收到的内容。
投影成本因此是一个独立的、必须单独盯住的指标——它直接决定缓冲能开多大。

```
视图投影基准  载荷 128 B/条（遮成可打印 ASCII，一条一行）
      行数    整批 ms 折合 µs/条 文档行数 MiB 字符
      2000       564.5        282.3         2000       0.30
     16000       101.2          6.3        16000       2.43
     32000       205.8          6.4        32000       4.87
     64000       428.2          6.7        64000       9.76
    128000       884.2          6.9       128000      19.55

成本分解（128000 条）
  ① 只解码切行               107.5 ms  (0.8 µs/条)
  ② 写进未上屏文本框        1036.7 ms  (8.1 µs/条)
  ③ 写进已上屏文本框        1068.2 ms  (8.3 µs/条)
  ②-① = 文档写入 7.3 µs/条   ③-② = 上屏 0.2 µs/条

微实验：文档写入的固定开销（5000 行 × 3 次插入/行，行内 32 字符）
  setCharFormat + insertText（无编辑块） 1506.8 ms  100.45 µs/次插入
  整段包一层 editBlock                    25.4 ms    1.69 µs/次插入
  insertText(text, format) 重载           1476.6 ms   98.44 µs/次插入
  editBlock + 重载                        26.9 ms    1.79 µs/次插入
```

三点读法：

- **成本与行数线性**（µs/条 稳定在 6.3–6.9），所以"预算开多大"可以直接换算成"点一下要等多久"。
  当前 `TrafficModel::kRowBudget = 50000` 就是按这条曲线定的：约 350 ms。
- **瓶颈过去全在"每次插入的固定开销"上**。不在编辑块里的每一次 `insertText` 都会单独
  结算一整轮文档变更（排版标脏 + 尺寸信号 + 滚动条重算），固定约 100 µs/次，而插入
  本身只要 1~2 µs；一条消息做 4~7 次插入，于是 360 µs/条里 250 µs 是纯开销。
  把整批包进 `beginEditBlock/endEditBlock` 后是 1.7 µs/次（**约 62 倍**），
  128000 条从约 46 s 降到 884 ms。**这条优化是"重投影全部历史"能成立的前提，
  动 `TrafficTextView::appendMessages` 时不要把它拆掉。**
- **微实验的探针必须逐行插块分隔符**。不插换行的话 N 次插入全落在同一个块里，
  变成一条几十万字符的长行，量到的是"超长单块"的布局成本，与真实的
  "一条消息一个块"完全不是一回事（这个坑第一次就踩了，输出直接消失）。

### 本机历史数据（文本台实现，1 KB 报文，每批 20 条）

| 实现 | 合计/周期 | 净工作 | 超 100ms |
| --- | --- | --- | --- |
| 无编辑块（34 万行文本台） | 64.4 ms | 4.5 ms | 0 / 200 |
| **加编辑块（现方案）** | **33.1 ms** | 7.0 ms | **0 / 200** |

"净工作"两项之差见上一节的口径说明：真实结论要看合计与落盘延迟，是对的更快了。

**不看平均值，看长尾。** `超过 100ms 的周期` 必须是 0：串口 115200 波特率下 1 KB 报文
约 11 条/秒，一帧多半 0~1 条；基准里每拍 20 条 ≈ 1250 条/秒，是串口做不到的速率，
用来留余量可以，用来判断真机体验会高估开销。

## B. 真实端点灌数据

`performance_test.py` 往 TCP Server 持续发包，配合真实界面观察。适合真机与长稳，
但不适合做改动回归：它依赖人工看"卡不卡"，没有可比的数字。

```bash
# 1. 启动 easyDebug，端点 A 配 TCP Server 监听 5000 并打开
# 2. 监视区开启"自动换行"
python tests/performance_test.py
```

脚本自带两个场景：50 ms/包 × 10 s、20 ms/包 × 5 s。
串口场景把 `--sample` 之类的手工步骤替掉即可：用真实串口设备按相同速率发数据。

### 观察清单

- 界面响应：点击、滚动、切页无延迟。
- 跟随最新：勾选"滚动到底"时应始终贴近最新记录，不出现"跳回中间"。
- 内存：稳定，不随记录数持续增长（模型上限 16 MiB / 5 万条 + 文本视图自身预算）。
- 重投影：切显示设置、改过滤条件后点"应用过滤"，界面停顿时长应与缓冲条数成正比
  （5 万条约 350 ms），不出现秒级冻结。

## 功能回归

性能改动必须跑功能回归，重点是显示契约与"视图 = 投影"的契约：

```powershell
cd build\ui-tests
.\release\easyDebug_ui_tests.exe -platform windows -o run.txt,txt
```

预期：`68 passed, 0 failed`。与性能/内存契约直接相关的用例：

- `historyBudgetAlsoLimitsRowCount`：先灌到超过预算，然后模型必须停在
  `TrafficModel::kRowBudget` 且保留最新的一批。断言用常量而不是写死数字，
  改预算时它不该以"失败"的面目出现。
- `textViewFollowsRetainsAndRollsBack`：模型触顶淘汰之后，**文本历史一行不少**，
  滚回顶部第 1 条仍可回看；跟随开启时钉底。
- `displaySettingsApplyToAlreadyReceivedRows`：切显示开关必须重排**已经收到**的行
  （关掉时间戳后旧行的时间戳要消失、打开 HEX 对照后旧行要长出对照行），
  且重投影后行号仍从 1 连续、HEX 对照行比数据行浅。
- `rebuildAppliesConditionsToExistingRecords`：过滤条件只作用于新行，
  点"应用过滤"才补到已有记录上。

核心测试：`build\core-tests\release\easyDebug_core_tests.exe -platform windows -o core.txt,txt`，
预期 `14 passed, 0 failed`。
