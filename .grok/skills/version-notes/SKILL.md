# 更新记录

版本记录是给使用者看的变更清单，不是提交说明，也不是设计文档。

## 文件

- 路径：仓库根目录 `更新记录.md`。已有同用途文件时沿用那个文件，不另起一份。
- 编码：UTF-8。
- 最新版本在文件最上面。新版本整段插到文首，旧段原样留下。

## 一条记录的形状

```markdown
# V<yyyyMMddHHmm>.<主>.<次><修订>

1.做了什么

2.做了什么
```

- 标题以 `# V` 开头，后面不加日期、作者或“发布说明”。
- 时间戳 12 位：年 4 位、月 2 位、日 2 位、时 2 位、分 2 位。用定版当时的本地时间，不补秒。
- 时间戳后是一个点，再接版本号。版本号三段直接拼在一起，每段至少 3 位、不足补 0。`1.0.0` 写成 `001.0000`，所以完整标题形如 `V202610111430.001.0000`。`0.1.0` 写成 `000.0010`。
- 版本号以 `version/version.h` 里三个 `#define` 为准。定版不递增这三个数，除非用户明确要求改版本。
- 标题下一行空着，然后是编号列表。编号从 1 连续递增，编号和正文之间不加空格：`1.修正……`。
- 一条只写一件用户能感知的事。多件事拆成多条，不把设计理由、文件名、函数名写进去。
- 用完成时，写结果。例：`1.设置菜单按显示前缀、显示选项和日志分成四段`。不写“本次重构了 QAction”。
- 修正类写成“修正……的问题”或“修正……时……”。新增类直接写新增了什么。
- 不写空标题、不写“其他优化”“代码整理”这类看不出变化的句子。内部重构没有用户可见结果时不记。

## 定版顺序

用户要求审查、定版、写记录、提交时，按这个顺序，不并行跳步：

1. 审查当前要定版的改动。有会挡住使用的缺陷时先停下来说明，不写记录、不提交。
2. 清理 `docs/`。对照当前代码删掉已经过时的文档和段落，把还在用的文档改成和程序一致。版本记录只写根目录 `更新记录.md`，不在 `docs/` 再留一份变更清单、旧版发布样例或“以后再做”的阶段计划。每次更新、定版、打包之前都做这一步。
3. 确认 `version/version.h` 的主/次/修订就是要固定的号。三个数字保持手改值。需要刷新时间戳时跑 `version/stamp_version.bat`，它只改时间戳和由版本号拼出来的字符串。
4. 用上面的标题格式把本版条目插到 `更新记录.md` 文首。条目覆盖这一版相对上一版的用户可见变化。
5. 提交时把版本头、更新记录、清理后的文档和对应代码放进同一次提交。提交说明仍遵循仓库既有风格。用户没要求推送时只提交到本地。

## 文档清理

留在 `docs/` 的是当前还成立的说明：架构、界面约定、开发验证、OTA 流程、参考来源。

删掉这些：

- 描述已经下线的步骤、旧版本号示例、已经做完却仍写成“待实现”的计划。
- 某一次审查或测量的归档。结论如果还成立，收进现行文档里的一两句。
- 外部工程的逐文件指纹、空目录、没有正文引用的附件。
- 和根目录 `更新记录.md` 重复的变更清单。

改写时只改失实的句子。不要为了统一口吻重写整篇还在用的文档。删文件前先搜仓库里的链接，把 README、测试说明和 OTA 文档里的引用一起改掉。

## 发行版信息

用户要发布版本、创建发行版，或说「生成发行版信息」时，按 Gitee「创建发行版」页的字段写好，方便直接粘贴。不代替用户点「创建发行版」，除非用户明确要求代为创建。

字段固定为：

- 标签：`v` 加 `version/version.h` 的 `主.次.修订`，例如 `v1.0.0`。
- 目标：`master`。
- 发行版的标题：`更新记录.md` 文首当前这一版的标题，去掉开头的 `# `。例如记录是 `# V202610111436.001.0000` 时，标题填 `V202610111436.001.0000`。标题不写 `v1.0.0`，那是标签。
- 预览版本：不勾选。
- 描述：`更新记录.md` 文首当前这一版的整段，从 `# V` 标题到该版最后一条，原样照抄，不改编号、不补空格、不另写摘要。
- 附件：`build/ota/QQCom-<版本>-win64.zip` 的完整路径。包还没打时先说明，不编造文件名。包已打出时附上字节数和 SHA-256，数字只取 `build/ota/manifest.json` 或当次打包输出。

创建发行版只是把 zip 挂到标签上。旧版本检查更新读的是 `master` 上的 `ota/stable.json`，不读发行版页面。附件公开下载、大小和 SHA-256 与 `build/ota/manifest.json` 一致后，把这份清单原样写成 `ota/stable.json` 并推到 `master`。清单里的 `version` 必须高于旧客户端里的版本号；只推源码或只建发行版，旧客户端仍会显示已是最新版本。
