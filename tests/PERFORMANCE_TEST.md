# 监视区刷新性能测试

两种测法，用途不同：

| 方式 | 测什么 | 何时用 |
| --- | --- | --- |
| **A. 基准程序**（`tests/perf`） | 刷新周期的净工作耗时，可重复、可 A/B | 改动了面板/模型/视图后回归 |
| **B. 真实端点灌数据**（`tests/performance_test.py`） | 真实串口/TCP 端到端观感 | M6 压测、真机长稳 |

---

## A. 基准程序（推荐）

直接编译真实的 `MainWindow` + `TrafficPanel`，按"每 16 ms 一批、每批 N 条"灌数据，
测每个刷新周期（追加 → 入模 → 滚底 → 重绘）的耗时。**测的就是出货代码**，
不是用假模型搭的近似复现——卡顿来自面板与视图的协作方式，假模型测不到同一个瓶颈。

mkdir build\perf ; cd build\perf
C:\MyProgram\Qt\6.10.1\msvc2022_64\bin\qmake.exe -o Makefile ..\..\tests\perf\traffic_perf.pro `
    -spec win32-msvc "CONFIG+=release" "CONFIG-=debug"

### 运行

```powershell

```

窗口会真实显示（字体度量要跟实际一致），跑完自动退出。

### 判读

主判据只有一条：**"净工作"必须稳定小于 16 ms**（一帧的预算）。
超过它就意味着 GUI 线程追不上消息节奏，队列越积越多，表现为卡顿、发木。

```
刷新周期（追加 → 入模 → 滚底 → 重绘）
  合计   mean    33.06 ms   p50    32.96   p95    34.48   max     36.09 ms
  净工作 mean     7.02 ms   （已扣除每拍刻意等待攒批的 26.0 ms）
  超过 100ms（肉眼可见卡顿）的周期 0 / 200
  帧率 净工作折合 142.4 fps   最差一拍  27.7 fps
```

- **净工作 = 合计 − 每拍等待**。这笔"等待"里其实**包含了插入本身**（攒批定时器
  就是在 processEvents 里触发的），所以它是个"差值"，把一个快得多的插入实现
  算成"等待变短、净工作变大"。**改插入路径时不要只看净工作，要连着"合计"一起看**：
  编辑块优化那次净工作从 4.5 涨到 7.0 ms，而合计从 64.4 降到 33.1 ms、
  落盘延迟从 60 ms 降到 26 ms——真实情况是快了约一倍。
  净工作适合当"帧预算还够不够"的绝对参考，不适合做两个差异很大的实现的 A/B。
- **超过 100ms 的周期**：长尾。用户感知到的正是这个数，它必须是 0。
- **拖动窗口**：跟随开启 + 历史就位下连续改尺寸 ±350px 的同步重绘耗时（本机 mean 15.3 ms）。

### 投影基准（第 5 个参数）

监视区是模型缓冲的**投影**：显示设置、编码格式、过滤条件变化都要重画已收到的内容。
投影成本因此是一个独立的、必须单独盯住的指标——它直接决定缓冲能开多大。

```
视图投影基准  载荷 128 B/条（遮成可打印 ASCII，一条一行）
      行数    整批 ms 折合 µs/条 文档行数 MiB 字符
      2000       564.5        282.3         2000       0.30
     16000       101.2          6.3        16000       2.43
     32000       205.8          6.4        32000       4.87
     64000       428.2          6.7        64000       9.76
    128000       884.2          6.9       128000      19.55

成本分解（128000 条）
  ① 只解码切行               107.5 ms  (0.8 µs/条)
  ② 写进未上屏文本框        1036.7 ms  (8.1 µs/条)
  ③ 写进已上屏文本框        1068.2 ms  (8.3 µs/条)
  ②-① = 文档写入 7.3 µs/条   ③-② = 上屏 0.2 µs/条

微实验：文档写入的固定开销（5000 行 × 3 次插入/行，行内 32 字符）
  setCharFormat + insertText（无编辑块） 1506.8 ms  100.45 µs/次插入
  整段包一层 editBlock                    25.4 ms    1.69 µs/次插入
  insertText(text, format) 重载           1476.6 ms   98.44 µs/次插入
  editBlock + 重载                        26.9 ms    1.79 µs/次插入
```

三点读法：

- **成本与行数线性**（µs/条 稳定在 6.3–6.9），所以"缓冲留多长"可以直接换算成"点一下要等多久"。
  早先 `TrafficModel` 用 5 万条 / 16 MiB 的预算把重投影压在 350 ms 内；**r6 已撤回这个取舍**：
  缓冲默认不设小上限（只在内存安全阀处才裁），历史长度优先，重投影因此随会话增长——
  跑到安全阀附近就是秒级。要把它拉回来得靠后台/分片投影，而不是再把缓冲改小。
- **瓶颈过去全在"每次插入的固定开销"上**。不在编辑块里的每一次 `insertText` 都会单独
  结算一整轮文档变更（排版标脏 + 尺寸信号 + 滚动条重算），固定约 100 µs/次，而插入
  本身只要 1~2 µs；一条消息做 4~7 次插入，于是 360 µs/条里 250 µs 是纯开销。
  把整批包进 `beginEditBlock/endEditBlock` 后是 1.7 µs/次（**约 62 倍**），
  128000 条从约 46 s 降到 884 ms。**这条优化是"重投影全部历史"能成立的前提，
  动 `TrafficTextView::appendMessages` 时不要把它拆掉。**
- **微实验的探针必须逐行插块分隔符**。不插换行的话 N 次插入全落在同一个块里，
  变成一条几十万字符的长行，量到的是"超长单块"的布局成本，与真实的
  "一条消息一个块"完全不是一回事（这个坑第一次就踩了，输出直接消失）。

### 本机历史数据（文本台实现，1 KB 报文，每批 20 条）

| 实现 | 合计/周期 | 净工作 | 超 100ms |
| --- | --- | --- | --- |
| 无编辑块（34 万行文本台） | 64.4 ms | 4.5 ms | 0 / 200 |
| **加编辑块（现方案）** | **33.1 ms** | 7.0 ms | **0 / 200** |

"净工作"两项之差见上一节的口径说明：真实结论要看合计与落盘延迟，是对的更快了。

**不看平均值，看长尾。** `超过 100ms 的周期` 必须是 0：串口 115200 波特率下 1 KB 报文
约 11 条/秒，一帧多半 0~1 条；基准里每拍 20 条 ≈ 1250 条/秒，是串口做不到的速率，
用来留余量可以，用来判断真机体验会高估开销。

## B. 真实端点灌数据

`performance_test.py` 往 TCP Server 持续发包，配合真实界面观察。适合真机与长稳，
但不适合做改动回归：它依赖人工看"卡不卡"，没有可比的数字。

```bash
# 1. 启动 easyDebug，端点 A 配 TCP Server 监听 5000 并打开
# 2. 监视区开启"自动换行"
python tests/performance_test.py
```

脚本自带两个场景：50 ms/包 × 10 s、20 ms/包 × 5 s。
串口场景把 `--sample` 之类的手工步骤替掉即可：用真实串口设备按相同速率发数据。

### 观察清单

- 界面响应：点击、滚动、切页无延迟。
- 跟随最新：勾选"滚动到底"时应始终贴近最新记录，不出现"跳回中间"。
- 内存：随会话线性增长（这是"不丢数据"的代价），到安全阀才停：模型 512 MiB / 2000 万条，
  文本视图 400 万块 / 5.12 亿字符。触顶时状态栏必须出现 `· 缓冲区已满`，不许无声丢数据。
- 重投影：切显示设置、改过滤条件后点"应用过滤"，界面停顿时长应与缓冲条数成正比
  （5 万条约 350 ms）。r6 之后缓冲可以很长，所以**长时间压测下的秒级停顿属已知代价**；
  验证点是"释放有播报"而不是"永远不卡"。

## 功能回归

性能改动必须跑功能回归，重点是显示契约与"视图 = 投影"的契约：

```powershell
cd build\ui-tests
.\release\easyDebug_ui_tests.exe -platform windows -o run.txt,txt
```

预期：全部通过（当前 **73 passed, 0 failed**；用例数会随契约沉淀增长，别把它当固定数字）。与性能/内存契约直接相关的用例：

- `historyBudgetAlsoLimitsRowCount`：先灌到超过预算，然后模型必须停在预算内且保留最新的一批。
  默认预算是安全阀（2000 万条，用例填不满），所以用例自己 `setBudget()` 注入小预算——
  被测的是淘汰语义，不是那个数字。
- `textViewFollowsRetainsAndRollsBack`：模型触顶淘汰之后，**文本历史一行不少**，
  滚回顶部第 1 条仍可回看；跟随开启时钉底；状态栏同时出现 `· 缓冲区已满`。
- `textViewBudgetReleaseIsReported`：文本视图的安全阀触发时同样要记账并播报
  （`releasedBlocks()` / `blocksReleased`），且只从最旧一端释放。
- `logRecordingReopensOnSessionBoundaries`：记录文件在三个会话边界（启动 / 清空 / 手动开启）
  都新建 `<模板基名>-yyyyMMdd-HHmmss.<扩展名>`——模板文件不被改写也不被追加，
  新文件从 `# easyDebug <时间> 格式=<X>` 头开始，清空后换新文件且记录开关保持勾选。
- `appearanceReprojectKeepsRowSetAndPendingHint` + QA 独立用例
  `appearanceReprojectIndependenceQa` / `appearanceReprojectFormatDependentCandidatesQa`：
  **外观重投影只换长相、不换条件**——敲关键词不点应用再改外观，行集不变且
  「应用过滤 •」仍在；点应用后才收窄、提示转干净。最后一条用例同时钉住 §3.3 的
  已知边界：只在格式专属渲染里命中的条件会随编码格式移动命中的行
  （例：DEC 下搜 `255` 命中 3 条，切 HEX 后剩 0 条——这是同一条件的重新求值）。
- `displaySettingsApplyToAlreadyReceivedRows`：切显示开关必须重排**已经收到**的行
  （关掉时间戳后旧行的时间戳要消失、打开 HEX 对照后旧行要长出对照行），
  且重投影后行号仍从 1 连续、HEX 对照行比数据行浅。
- `rebuildAppliesConditionsToExistingRecords`：过滤条件只作用于新行，
  点"应用过滤"才补到已有记录上。

核心测试：`build\core-tests\release\easyDebug_core_tests.exe -platform windows -o core.txt,txt`，
预期 `14 passed, 0 failed`。

## C. 端到端压测（带事件循环延迟探针）

> 本节只定**流程与判据**；各阶梯的具体数字（P99、吞吐上限、浸泡拐点）由 QA 实测产生后回填，
> 不要拿这里的历史数字当承诺值。

### 目的

把"卡不卡"从人工目测换成可量化的 GUI 事件循环延迟：探针在 GUI 线程挂一个 20ms QTimer，
每一拍记"实际触发时刻 − 理论时刻"的偏差（µs，自校正、不累积漂移），每 500ms 聚合一行
`<epoch_ms> <样本数> <P50> <P95> <P99> <MAX> <总条数> <总字节>`（毫秒，一位小数）追加到文件。
迟滞直接反映界面线程被长任务占住的程度，是用户感知卡顿的代理量。行尾两个字段供压测脚本
对账：`sent_packets` / `sent_bytes` 直接比 `<总条数>` / `<总字节>`，免去截图读状态栏
（透传组帧下条数≠包数，对账以 `<总字节>` 为准）。

### 启动（带探针）

```powershell
# Git Bash 里 GUI 日志不可见，探针只写文件，所以必须给 --latency-probe
.\easyDebug.exe --latency-probe <输出文件>

# test-only：启动即把端点 A 打开，省去截图/点坐标驱界面
.\easyDebug.exe --auto-open tcp-server:9000 --latency-probe <输出文件>
```

- `--auto-open`（test-only）语法：`tcp-server:<port>` / `udp:<port>` / `tcp-client:<host>:<port>` /
  `serial:<name>`；把端点 A 草稿设为对应类型并走与"打开 A"按钮完全相同的 open 路径。
  不传零行为；解析失败 `qWarning` 后忽略。
- 探针只在显式传参时开启：不传时一个定时器都不开，正常运行零开销。
- 文件打不开会 `qWarning` 后忽略（探针失败不阻断启动）。
- 输出文件持续追加：每轮压测用新文件，别把多轮结果混在一起。

### 端点配置

- **TCP Server**：端点选「TCP 服务器」，地址 `127.0.0.1`、端口按需（如 5000），点「监听」。
- **UDP**：端点选「UDP」，本地地址 `127.0.0.1`、绑定端口按需，点「绑定」。
- 压测建议同时开启「记录到文件」：日志里的 RX 行数与脚本 `sent_packets` 对账，判断丢数。

### 发压

```bash
# 仓库自带 Python 环境（纯标准库脚本）
python tests/stress/traffic_stress.py --proto tcp --host 127.0.0.1 --port 5000 \
    --rate 500 --size 256 --duration 30
python tests/stress/traffic_stress.py --proto udp --host 127.0.0.1 --port 5000 \
    --rate 2000 --size 1024 --duration 60 --ramp
```

每条报文 = `<8 字节递增序号><8 字节毫秒时间戳><填充>`；结束打印
`sent_packets / sent_bytes / actual_rate`，与 easyDebug 的 RX 计数（或记录文件的 RX 行数）对账。

### 速率阶梯（建议）

每条字节数 × 速率：`64B / 256B / 1KB` × `100 / 500 / 1k / 2k / 5k / 10k` 条/秒。
每档先跑 30s 观察稳定性；`--ramp` 用于找"从多少速率开始 UI 明显掉速"的爬坡形态。
每档记录：探针 P50/P95/P99/MAX、app 是否跟上（RX 对账）、是否出现 `· 缓冲区已满`。

### 卡顿判定

**单秒窗口的探针 P99 > 50ms 判为卡顿。** 探针每 500ms 一行、两行 ≈ 1 秒；任一窗口
P99 > 50ms 即该秒卡顿。连续多秒卡顿、或 P50 持续抬升，视为速率达到 GUI 上限。

### 长时浸泡

固定一个"已明显有压力但仍能跟上"的速率，跑 ≥ 1 小时，找累计规模开始影响流畅度的拐点
（重投影随条数线性变慢，r6 之后缓冲很长，这是"不丢数据"明码标出的代价）。拐点判据：
同一速率下，探针 P50/P99 随会话条数增长持续抬升；或交互（切格式、应用过滤）的停顿从
"几十毫秒"进入"秒级"。触顶时状态栏必须出现 `· 缓冲区已满`，不许无声丢数据。

### 冒烟结果（工程师自证链路通，2026-10-04 实测；全量阶梯由 QA 跑）

TCP 500 条/秒 × 30 秒 × 256 B/条（端点 A = TCP 服务器 127.0.0.1:9000，默认透传组帧）：

- 脚本输出：`sent_packets=15000 sent_bytes=3840000 errors=0  actual_rate=500.0 pkt/s`。
- app 状态栏：`RX 3.7 MB · 0 B/s`（3 840 000 B = 3.66 MB → 3.7 MB），**字节级对账一致，零丢失**。
  条数为 10411：透传组帧下 TCP 把 500 条/秒的突发合并成 readyRead 批次，
  条数不等于包数属预期，对账以字节为准。
- 探针文件持续增长（30 秒压测窗口内 44 行），全部样例 P99 < 26 ms，远低于 50 ms 卡顿线：

```
1791128045751 25 11.7 12.6 12.8 12.8
1791128047309 25 11.6 12.3 21.0 21.0
1791128059844 25 11.6 12.2 25.7 25.7   ← 压测窗口内最差一拍
1791128072343 25 11.8 12.4 25.2 25.2
```

（字段含义见"目的"一节：epoch_ms 样本数 P50 P95 P99 MAX 总条数 总字节，毫秒一位小数。）
