# 监视区过滤功能设计

状态：设计已定稿 r2（五项决策见 §10，均已确认）。日期：2026-10-04。r2 修订：过滤条形态由"顶栏按钮 + 折叠多行面板"改为**单行常驻条**（§7.1、§10 决策 5）。前置阅读：`PLAN.md` R06、`docs/UI_DESIGN.md` §4/§9.2、`docs/ARCHITECTURE.md` 监视区章节。

## 1. 目标与非目标

**目标**：让用户在 34 万行的实时流里快速聚焦到自己关心的那部分——按内容、方向、端点、事件类型、长度、对端、帧类型收窄显示，条件可组合、可排除、可持久化。

**非目标**：

- 不改通信行为。过滤只作用于**显示**，不影响收发、转发、记录、统计（沿用 R06 与 UI_DESIGN §4 的既有约定）。
- 不做服务端式规则引擎、不做跨会话的历史检索（属于未来的记录检索功能）。
- 不引入对全量文档的逐行扫描——这是与"数据性能优先"直接冲突的做法（见 §6）。

## 2. 现状与约束

现状（`TrafficPanel` + `TrafficFilter`）：

| 能力           | 现状                                         |   | 问题                 |
| ------------ | ------------------------------------------ | - | ------------------ |
| 搜索框          | 单个关键词，匹配当前格式渲染文本 / UTF-8 / HEX 两种写法 / 对端地址 |   | 只能 1 个词，无法排除，无组合   |
| 端点 / 方向 / 事件 | A、B、RX、TX、错误日志 5 个开关                       |   | 只有布尔维度，没有长度、对端、帧类型 |
| 生效时机         | **到达时判定**（控制台语义），已固化行不重排                   |   | 改条件后旧行仍在，看不到"过滤结果" |
| 计数           | 只有会话累计条数                                   |   | 看不到"被过滤掉多少"        |

三条硬约束（不得违背）：

1. **性能**：判定在每条消息到达时执行一次，必须短路、预编译、无 O(全表) 操作。
2. **控制台语义**：行按到达时的格式与开关固化；行号是会话内绝对计数。
3. **两套预算不对称**：文本视图 100 万行 / 2.56 亿字符；结构化模型只有 2 万条 / 4 MiB。**"回溯重建"只能拿到模型里保留的那部分**——这是本设计的核心约束，也是 §5 语义方案的分水岭。

## 3. 过滤模型

### 3.1 条件（Rule）

全部条件作用在 `Traffic::Message` 的**结构化字段**上，不解析显示文本（与现有 `TrafficFilter::accepts` 同源）。

| 维度   | 取值                        | 说明                             |
| ---- | ------------------------- | ------------------------------ |
| 方向   | RX / TX / 状态 / 警告 / 错误    | 多选，命中任一即通过                     |
| 端点   | A / B                     | 复用监视区既有的 A/B 开关，不重复设条件         |
| 事件类型 | 状态迁移 / 警告 / 错误            | 与"显示错误日志"开关同源                  |
| 长度   | min..max 字节               | 用 `displayBytes()`（真实长度，非预览长度） |
| 对端   | 子串匹配 `source.peerAddress` | TCP 服务器/UDP 才有值                |
| 帧类型  | 流片段 / 数据报 / 完整帧           | `Framing` 枚举，排障时"只看完整帧"很常用     |
| 来源   | 自动 / 手动 / 定时 / 转发 / 示例    | 可选，用于排除自己发出的内容                 |

### 3.2 组合（Spec）

```cpp
struct FilterRule {          // 一条结构化条件
    Field field;             // Direction / EventClass / Length / Peer / Framing / Origin
    QString value;           // 长度用 "min-max"，其余用枚举名或子串
    bool enabled = true;     // 临时关闭单条，不必删除
};

struct FilterSpec {
    QList<FilterRule> requires;   // 全部满足（AND）
    QList<FilterRule> excludes;   // 命中任一即排除（黑名单）
    QList<QString> keywords;      // 任一命中即可（OR，空 = 不按内容过滤）
    QList<QString> vetoes;        // 命中任一即排除的关键词
    bool caseSensitive = false;
    bool regex = false;           // keywords/vetoes 按正则解释
};
```

语义：`(keywords 命中任意) AND (requires 全部满足) AND (不在 excludes 内) AND (不含 vetoes)`。  
`keywords` 与 `requires` 分开是因为**组内 OR / 组间 AND** 是用户唯一能自然理解的心智模型（"包含 A 或 B，但不要 C"）。

### 3.3 唯一判定点

沿用现有约定：**判定只在 `TrafficFilter::accepts(record, spec, format)` 一处实现**，UI 不另写匹配逻辑；`Options` 由 `Spec` 派生（A/B、RX/TX、事件开关本身就是 `requires` 的快捷形态，两者共用同一份判定与同一份持久化）。

## 4. 过滤与"搜索"的关系（已确认：合并）

搜索框升级为过滤的一部分，不再有第二套语义：

- 搜索框 = `keywords` 的快捷输入（空格 / 换行分隔多个词，全部 OR）；
- 过滤条里编辑 `keywords` 时，其词 chip 与输入框文本双向同步（同一份数据的两种视图，见 §7.2）；
- 保留独立输入框的原因是**高频快捷键位**：`Ctrl+F` 聚焦、回车即刻收流，不必进浮层。

## 5. 生效时机（关键决策）

| 方案                      | 行为                            | 成本                                                                        | 数据源                          | 结论                                                           |
| ----------------------- | ----------------------------- | ------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------ |
| **A. 仅新行**（现状语义）        | 改条件只影响之后到达的行                  | 0                                                                         | —                            | 最小改动，但用户改完条件看到的还是旧内容，体验割裂                                    |
| **B. 新行 + 显式回溯重建**（已选定） | 过滤条上点 `重建视图`：清空视图 → 从模型重放命中项 | 清空是一次整块释放；重放 ≤ 2 万条 ≈ 60–120 ms（与文本历史长度无关，只与模型预算有关）                       | `TrafficModel`（2 万条 / 4 MiB） | 语义诚实、实现零新路径（复用 `appendMessages`），代价是**只回溯模型保留范围**，必须在 UI 上写明 |
| C. 全量回溯                 | 理想语义                          | 需要把结构化历史提升到与文本同级：100 万行 × 每条 Message 元数据（时间、来源、三个 QUuid、两个 QString）≈ GB 级 | 新增 second store              | 与"数据性能优先"直接冲突，否决                                             |

**决策：方案 B（新行生效 + 显式回溯重建）**，并把限制显式化：

- 单行条上没有位置放常驻说明，范围写进 `重建视图` 的 tooltip："仅回溯最近 2 万条 / 4 MiB 内的记录，约 0.1 秒"；
- 重建后状态栏摘要播报："已重建视图 · 显示 N 条（模型保留范围内匹配）· 更早记录已清理"；
- 重建后行号按重建结果连续重排（`TrafficTextView::appendMessages` 增加起始行号参数），摘要里注明"行号为重建后序号"；
- 需要更长历史的用户有明确出口：开启"记录到文件"（全量落盘，不受过滤影响）。

## 6. 性能预算与实现要点

- 每条消息判定：条件数 × 短路；典型 < 1 µs。**必须**保证：
  - 正则表达式在条件变更时用 `QRegularExpression` 预编译一次，热路径只 `match()`；
  - HEX 串**惰性构造**——只有存在"内容按 HEX 匹配"的条件时才把 `raw` 转成 HEX（现状 `accepts` 无条件构造两次 HEX 串，是既有的可优化点）；
  - 被禁用（未勾选）的条件不参与判定；
  - 长度条件是整数比较，不构造字符串。
- 明确不做：按行扫描文档、全表高亮、每条消息重建视图、为过滤复制一份原始字节。
- 命中高亮（F2）：只对**新追加的行**做，代价 O(命中数)；不对历史全表重刷。
- 计数：新增 `m_filteredOut`（被条件挡下的条数），状态栏摘要变为"共 N 条 · 过滤掉 M 条"，同时把"过滤生效中"体现在状态栏（避免用户以为掉数据）。
- perf 基准新增场景：`--filter 5`（5 个条件全开）下的净工作耗时，门槛沿用 < 10 ms/拍。

## 7. 交互设计

### 7.1 形态：单行常驻过滤条

过滤条**不是**"展开后压出一块多行面板"，而是**一条恒为单行的横向条件条**，固定在监视区顶栏正下方、数据区之上：

```text
┌ 监视区 ────────────────────────────────────────────────────────────────────────────────────────┐
│ [A][B] [UTF-8 ▼] [⚙显示设置] [导出] [↓滚动到底] [清空]                                          │ ← 顶栏
├ 过滤 ──────────────────────────────────────────────────────────────────────────────────────────┤
│ 过滤  关键词 [ 心跳 0D0A ▏] (心跳 ×)(0D0A ×)   排除 [ AA 55 ▏] (AA 55 ×) ╿ RX TX 状态 警告 错误 ╿ 更多条件(2) ▾ ╿ 重置  重建视图 │ ← 过滤条（恒一行）
├───────────────────────────────────────────────────────────────────────────────────────────────┤
│ 1  14:30:01.201 [4 B] RX: 01 02 03 04                                                          │ ← 数据区
└───────────────────────────────────────────────────────────────────────────────────────────────┘
```

（`╿` 仅为分组分隔线示意，实际是 1px 竖线。）

四条形态约束：

- **高度恒为一行**：与顶栏那一行等高（所有内联控件走同一套 18px 最小高度 / 4px 内边距规格，与端点行同一约定），不随窗口宽度、也不随条件数量变化；数据区不会被它挤动。
- **宽度铺满**：关键词输入框是唯一弹性项，吸收全部剩余宽度，其余元素按自身 `sizeHint` 紧凑排在右侧；**永不换行、永不出现横向滚动条**。
- **常驻不折叠**：一行的高度成本低于"展开/收起"的交互成本；渲染上它还顺带把原本藏在"显示设置"菜单里的 RX/TX 摆到明面。
- **零新增自绘**：元素只用 QSS 已覆盖的 `QPushButton` / `QLineEdit` / `QMenu`，不新增自绘控件、不写死像素。

**关于原顶栏搜索框**（修订已确认决策 #3 的形态）：关键词就是过滤条的第一格，顶栏不再重复放一个搜索框——搜索框原本占据顶栏唯一的弹性位置，把它连同"关键词"语义一起下移到过滤条，等于用同一行高度换到一整行的可用宽度。`Ctrl+F` 行为不变，只是焦点落到过滤条内的关键词输入框；`Ctrl+Shift+F` 不再需要（条常驻）。

> 若坚持顶栏保留搜索框，退化形态为：过滤条第 1 格只放 `关键词` 只读 chip 托盘（提示"见上方搜索框"），两份视图共用同一份 `keywords`。见 §10 决策 5。

### 7.2 单行条的解剖（从左到右）

| 组   | 元素                      | 控件                           | 宽度策略        | 说明                                                 |
| --- | ----------------------- | ---------------------------- | ----------- | -------------------------------------------------- |
| 标识  | `过滤`                    | 文字 + 漏斗图标                    | 定宽          | 这一条的自解释标签                                          |
| 内容  | 关键词输入                   | `QLineEdit`（带清空按钮）           | **弹性（吸收余量）** | 空格分隔多词、任一命中（OR）；`Ctrl+F` 的落点                        |
| 内容  | 关键词 chip                | `QPushButton`（点击即删）          | 按内容         | 与输入框文本是**同一份数据**的两种视图：文本分词得到 chip，点 chip 等于从文本里删掉该词 |
| 内容  | 排除词输入                   | `QLineEdit`                  | 定宽，最小 8em   | 命中即隐藏（黑名单）                                          |
| 条件  | `RX` `TX` `状态` `警告` `错误` | 可勾选 `QPushButton`             | 定宽（各约 2 字宽） | 方向维度：多选、命中任一即通过                                     |
| 条件  | `更多条件 (N) ▾`            | `QPushButton` + `StayOpenMenu` | 定宽          | 低频维度与匹配选项收进浮层；勾选不关闭，浮层不占布局高度                        |
| 动作  | `重置`                    | `QPushButton`                  | 定宽          | 清空全部条件（含浮层内的），回到不过滤                                  |
| 动作  | `重建视图`                  | `QPushButton`                  | 定宽          | 方案 B 的回溯重建；tooltip 写明"仅回溯最近 2 万条 / 4 MiB，约 0.1 秒"    |

`更多条件` 浮层内容（浮层纵向展开、浮在数据区之上，高度不受主条约束）：

```text
更多条件
├ 帧类型   ☑ 完整帧   ☐ 流片段   ☐ 数据报
├ 长度     [     ] ~ [     ] 字节
├ 对端     [ 192.168.1.            ]
├ 来源     ☑自动  ☑手动  ☑定时  ☑转发  ☐示例
└ 匹配     ☐ 区分大小写    ☐ 正则表达式
```

浮层里的每一项与主条上的 chip **共用同一份 `FilterSpec`**——浮层只是同一份状态的另一种呈现，不产生第二套布尔值。

**单一状态源**：`RX / TX / 状态 / 警告 / 错误` 五个开关只有一份状态。实现上仍是 `QAction`（沿用既有 `showRx` / `showTx` 等 objectName，既有用例与记忆可延续），菜单项与过滤条按钮绑定同一批 action，任何一处切换另一处同步。原"显示错误日志"这一个布尔拆成 `状态 / 警告 / 错误` 三个独立开关，`TrafficFilter::Options` 里的 `events` 由三值集合取代，相关断言按新开关改写。

### 7.3 宽度预算与折叠规则

| 可用宽度 | 形态                                                  |
| ---- | --------------------------------------------------- |
| 宽    | 全部摊开：关键词 + 排除 + 5 个方向 chip + 更多条件 + 重置 + 重建视图      |
| 中    | 方向 chip 收进 `更多条件` 浮层（浮层多一组"方向"），主条只留 `更多条件 (N) ▾` |
| 窄    | 关键词输入框压到最小宽度（8em）；chip 托盘显示前若干个 + `+N` 收纳             |

硬规则：**任何宽度下都保持单行**。折叠判据由各控件 `sizeHint()` 汇总得出，不写死像素阈值；宽/窄两套排布用 `QStackedLayout` 切换，切换只改可见性、不重建控件（避免热路径外的控件抖动）。

### 7.4 与"显示设置"的分工

| 面板   | 管什么        | 例子                                 |
| ---- | ---------- | ---------------------------------- |
| 显示设置 | **每行长什么样** | 行号、时间戳、方向、长度、HEX 对照、纯数据、自动换行、记录到文件 |
| 过滤   | **哪些行进来**  | 关键词、排除词、方向、端点、事件类型、长度、对端、帧类型       |

按这条线重新归位：**`RX` / `TX` / `状态` / `警告` / `错误` 从"显示设置"菜单迁入过滤条**（它们管的是"哪些行进来"，原本放错了地方），显示设置菜单随后只剩行内容开关与"记录到文件"，反而更短。`A` / `B` 端点开关仍留在顶栏左端（高频、且属于范围而非条件），过滤条不重复它们。

两者都在到达时生效，都不回溯（除非显式点 `重建视图`）。

### 7.5 反馈

- 条数摘要：`共 12,043 条 · 过滤掉 8,912 条`（进主窗口状态栏，不占面板空间），状态栏同时标记"过滤生效中"，避免用户以为掉数据；
- 条常驻后不需要"过滤·N"计数按钮——生效条件就摆在条上；只有 `更多条件 (N)` 显示浮层内生效的条件数；
- 条件本身显示为可删除条目（chip），不用弹窗确认；
- 正则非法时输入框红框 + 提示，且**该条件不参与判定**（退化为不过滤，绝不静默吞掉全部数据）；
- 空态提示随之变化："当前过滤条件下没有匹配记录"（而不是"等待接收数据"）。

## 8. 分期落地

| 阶段      | 内容                                                      | 完成判据                                |
| ------- | ------------------------------------------------------- | ----------------------------------- |
| F1 最小可用 | `FilterSpec` + 关键词/排除词/方向/端点/事件类型；到达时判定；**单行常驻过滤条**；持久化；过滤计数摘要 | 关键词与排除词组合正确；条件持久化跨启动；条在任何宽度下保持单行；perf 无回退       |
| F2 完整条件 | 长度范围、对端、帧类型、来源；命中高亮；回溯重建（方案 B）                          | 重建后显示数 = 模型内命中数；重建耗时 < 200 ms（2 万条） |
| F3 复用   | 命名过滤预设（保存/加载/切换）、条件导入导出、按端点独立过滤                         | 预设跨启动可用；切换预设即时生效                    |

## 9. 验收与测试点

UI 测试（`tests/ui`）：

1. 关键词多词 OR、大小写开关、正则非法回退（不吞数据）；
2. 排除词优先于关键词；
3. 方向 + 端点 + 事件类型的组合判定（复用 `structuredFiltersUseFactsNotLabels` 的事实字段断言风格）；
4. 长度范围边界（含 `displayBytes()` 而非预览长度）；
5. 条件持久化：重建面板后条件与搜索框一致；
6. 回溯重建：视图行数 = 模型内命中数，行号连续，摘要含过滤计数；
7. 空态提示随过滤条件出现；
8. **单行铁律**：窗口压到最小宽度时过滤条仍为一行（高度与顶栏一行相等、无横向滚动条、无换行），宽/窄两套排布切换后所有 chip 仍可点；
9. 关键词 chip 与输入框文本双向一致——改文本则 chip 随之增删，点 chip 则文本同步去掉该词；
10. `更多条件` 浮层勾选后不关闭，且浮层条件与主条 chip 同源（同一份 `FilterSpec`，不存在两套状态）。

性能：`build/perf` 增补"5 条件过滤"场景，净工作 < 10 ms/拍，且与文档行数无关。

| # | 议题    | 决策                                   | 影响                                                         |
