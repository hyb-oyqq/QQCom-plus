# 监视区刷新性能测试

两种测法，用途不同：

| 方式 | 测什么 | 何时用 |
| --- | --- | --- |
| **A. 基准程序**（`tests/perf`） | 刷新周期的净工作耗时，可重复、可 A/B | 改动了面板/模型/视图后回归 |
| **B. 真实端点灌数据**（`tests/performance_test.py`） | 真实串口/TCP 端到端观感 | M6 压测、真机长稳 |

---

## A. 基准程序（推荐）

直接编译真实的 `MainWindow` + `TrafficPanel`，按"每 16 ms 一批、每批 N 条"灌数据，
测每个刷新周期（追加 → 入模 → 滚底 → 重绘）的耗时。**测的就是出货代码**，
不是用假模型搭的近似复现——卡顿来自面板与视图的协作方式，假模型测不到同一个瓶颈。

### 构建

```powershell
# 需要 Qt + MSVC 环境；下面按本机路径，换机器时替换 Qt 路径
call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"
mkdir build\perf ; cd build\perf
C:\MyProgram\Qt\6.10.1\msvc2022_64\bin\qmake.exe -o Makefile ..\..\tests\perf\traffic_perf.pro `
    -spec win32-msvc "CONFIG+=release" "CONFIG-=debug"
nmake release
```

### 运行

```powershell

.\release\easyDebug_traffic_perf.exe 1024 20 120 1
.\release\easyDebug_traffic_perf.exe 4096 20 120 1
.\release\easyDebug_traffic_perf.exe 1024 20 120 0
```

窗口会真实显示（字体度量要跟实际一致），跑完自动退出。

### 判读

判据只有一条：**"净工作"必须稳定小于 16 ms**（一帧的预算）。
超过它就意味着 GUI 线程追不上消息节奏，队列越积越多，表现为卡顿、发木。

```
刷新周期（追加 → 入模 → 滚底 → 重绘）
  合计   mean    37.00 ms   p50    36.95   p95    39.95   max     41.70 ms
  净工作 mean    10.08 ms   （已扣除每拍刻意等待攒批的 26.9 ms）
  超过 100ms（肉眼可见卡顿）的周期 0 / 120
  帧率 净工作折合  99.2 fps   最差一拍  24.0 fps
```

- **净工作**：真正花在插入 / 布局 / 绘制上的时间。基准刻意每拍至少等 25 ms，
  好让（旧实现里的）200 ms 防抖定时器有机会触发，否则测不到"数据停顿才发作"的整秒冻结。
  这 25 ms 计在"合计"里、"净工作"里已扣除。
- **超过 100ms 的周期**：长尾。修复前 4 KB 报文这里会出现单次 3 s 以上的冻结。
- 末尾的 `resizeRowsToContents()` 参考值说明"逐行精确行高"这条路本身有多贵
  （本机约 0.9 ms/行，3212 行 ≈ 2.9 s）。现在的实现不再调用它，
  这个数字只是用来解释为什么不能走这条路。

### 本机历史数据

每帧净工作耗时（1 KB 报文，保留 1024–3212 条）：

| 显示形态 | 每帧净工作 | 一屏条数 |
| --- | --- | --- |
| 修复前（逐行重算行高） | 62.1 ms，最差一拍 **3779 ms** | 3 行 × 裁切 |
| 统一行高（已弃用） | 7.6–8.4 ms | 约 8 条 |
| **按内容定行高（现方案）** | **17.9–19.9 ms** | 短报文 34 条 / 长报文 8 条 |
| 换行关闭（参照） | 8.0–10.0 ms | 约 26 条 |

两点读法：

- **判据是"有没有长帧"，不是平均值。** `超过 100ms 的周期` 必须是 0：
  旧实现那一档会出现单次 3 秒以上的冻结，现在四档都是 0。
- **不要用"每拍 N 条"去推断真实场景。** 串口 115200 波特率下 1 KB 报文约 11 条/秒，
  一帧多半 0~1 条；基准里每拍 20 条 ≈ 1250 条/秒，是串口做不到的速率，
  用来留余量可以，用来判断真机体验会高估开销。
  实测"按内容定行高"的每帧开销与每拍条数基本无关（每拍 1/2/5/20 条都是 18–22 ms），
  说明它是视图在逐行不同行高下的固有开销，不是插入开销。

## B. 真实端点灌数据

`performance_test.py` 往 TCP Server 持续发包，配合真实界面观察。适合真机与长稳，
但不适合做改动回归：它依赖人工看"卡不卡"，没有可比的数字。

```bash
# 1. 启动 easyDebug，端点 A 配 TCP Server 监听 5000 并打开
# 2. 监视区开启"自动换行"
python tests/performance_test.py
```

脚本自带两个场景：50 ms/包 × 10 s、20 ms/包 × 5 s。
串口场景把 `--sample` 之类的手工步骤替掉即可：用真实串口设备按相同速率发数据。

### 观察清单

- 界面响应：点击、滚动、切页无延迟。
- 跟随最新：勾选"滚动到底"时应始终贴近最新记录，不出现"跳回中间"。
- 内存：稳定，不随记录数持续增长（历史上限 4 MiB + 缓存约 1 MB）。
- 暂停显示：勾选暂停后恢复，应展示恢复时刻的最新窗口并给出丢弃条数。

## 功能回归

性能改动必须跑功能回归，重点是自动换行的显示契约：

```powershell
cd build\ui-tests
.\release\easyDebug_ui_tests.exe
```

预期：`55 passed, 0 failed`。其中三个用例专门守卫本次的性能与内存契约：

- `trafficWrapSwitchAdjustsView`：换行开启后，**每一行的行高必须等于该行内容需要的
  行数 × 行高单位 + 绘制余量**（逐行独立）。退回统一行高、或把行数算错，都会失败；
  同时校验 1 KB 报文比十几字节的示例报文占更多行，且行数被 6 行上限钳住。
- `hugeMessagesRenderBoundedTextOnly`：4 KB 报文的绘制文本必须被裁剪且以省略号结尾，
  同时 `record.raw` 仍是完整 4096 字节、悬停提示仍含完整 HEX。
- `historyBudgetAlsoLimitsRowCount`：三万条 2 字节小报文之后模型必须停在 20000 条，
  且保留最新的一批。

核心传输测试：`build\core-tests\release\easyDebug_core_tests.exe`，预期 `10 passed`。
