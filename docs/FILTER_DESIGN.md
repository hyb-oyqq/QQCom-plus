# 监视区过滤功能设计

状态：**F1 已实现**（代码与测试均已落地）。日期：2026-10-04，末次修订 2026-10-04。前置阅读：`PLAN.md` R06、`docs/UI_DESIGN.md` §4/§9.2、`docs/ARCHITECTURE.md` 监视区章节。

修订沿革：

- r2：过滤条形态由"顶栏按钮 + 折叠多行面板"改为**单行常驻条**（§7.1、§10 决策 5）。
- **r3（本次）**：形态定为**两行头 + 可折叠单行过滤条**（用户钦定：固定两行、按钮折叠、全部按钮带 Material 字形）；同时把设计稿从"草图"对齐到实际落地的类与 API（§3.2/§3.3），并把 `重建视图` 回溯显式划归 F2（F1 只有"仅新行"语义）。

## 1. 目标与非目标

**目标**：让用户在 34 万行的实时流里快速聚焦到自己关心的那部分——按内容、方向、端点、事件类型、长度、对端、帧类型收窄显示，条件可组合、可排除、可持久化。

**非目标**：

- 不改通信行为。过滤只作用于**显示**，不影响收发、转发、记录、统计（沿用 R06 与 UI_DESIGN §4 的既有约定）。
- 不做服务端式规则引擎、不做跨会话的历史检索（属于未来的记录检索功能）。
- 不引入对全量文档的逐行扫描——这是与"数据性能优先"直接冲突的做法（见 §6）。

## 2. 现状与约束

现状（`TrafficPanel` + `TrafficFilter`）：

| 能力           | 现状                                         |   | 问题                 |
| ------------ | ------------------------------------------ | - | ------------------ |
| 搜索框          | 单个关键词，匹配当前格式渲染文本 / UTF-8 / HEX 两种写法 / 对端地址 |   | 只能 1 个词，无法排除，无组合   |
| 端点 / 方向 / 事件 | A、B、RX、TX、错误日志 5 个开关                       |   | 只有布尔维度，没有长度、对端、帧类型 |
| 生效时机         | **到达时判定**（控制台语义），已固化行不重排                   |   | 改条件后旧行仍在，看不到"过滤结果" |
| 计数           | 只有会话累计条数                                   |   | 看不到"被过滤掉多少"        |

三条硬约束（不得违背）：

1. **性能**：判定在每条消息到达时执行一次，必须短路、预编译、无 O(全表) 操作。
2. **控制台语义**：行按到达时的格式与开关固化；行号是会话内绝对计数。
3. **两套预算不对称**：文本视图 100 万行 / 2.56 亿字符；结构化模型只有 2 万条 / 4 MiB。**"回溯重建"只能拿到模型里保留的那部分**——这是本设计的核心约束，也是 §5 语义方案的分水岭。

## 3. 过滤模型

### 3.1 条件（Rule）

全部条件作用在 `Traffic::Message` 的**结构化字段**上，不解析显示文本（与现有 `TrafficFilter::accepts` 同源）。

| 维度   | 取值                        | 说明                             |
| ---- | ------------------------- | ------------------------------ |
| 方向   | RX / TX / 状态 / 警告 / 错误    | 多选，命中任一即通过                     |
| 端点   | A / B                     | 复用监视区既有的 A/B 开关，不重复设条件         |
| 事件类型 | 状态迁移 / 警告 / 错误            | 与"显示错误日志"开关同源                  |
| 长度   | min..max 字节               | 用 `displayBytes()`（真实长度，非预览长度） |
| 对端   | 子串匹配 `source.peerAddress` | TCP 服务器/UDP 才有值                |
| 帧类型  | 流片段 / 数据报 / 完整帧           | `Framing` 枚举，排障时"只看完整帧"很常用     |
| 来源   | 自动 / 手动 / 定时 / 转发 / 示例    | 可选，用于排除自己发出的内容                 |

### 3.2 组合（`Options`）

落到代码上只有**一份条件快照**，没有 `FilterRule` / `FilterSpec` 这类中间层——F1 的条件维度全是布尔或词表，套一层规则对象只会多一次遍历而没有任何表达力收益（`FilterRule` 留给 F2 的长度/对端/帧类型，那时才真的需要"字段名 + 值 + 启用位"）：

```cpp
struct Options {                    // 一份条件快照，由条件条收集、由 Matcher 消费
    QSet<QUuid> endpoints;          // 端点；空集 = 该死，什么都不过
    bool rx = true;                 // 方向：RX / TX
    bool tx = true;
    bool states = true;             // 事件类型：状态迁移（端口打开/关闭/重连）
    bool warnings = true;           // 警告日志
    bool errors = true;             // 错误日志
    QStringList keywords;           // 内容：任一命中即通过（组内 OR，空 = 不过滤内容）
    QStringList excludes;           // 内容：命中任一即隐藏（黑名单）
    bool caseSensitive = false;
    bool regex = false;             // keywords / excludes 按正则解释
};
```

语义（一条记录按顺序判定）：

```text
端点命中 AND 方向命中 AND 事件类型命中 AND (keywords 为空 或 命中任一) AND (无法命中 excludes)
```

**组内 OR / 组间 AND** 是用户唯一能自然理解的心智模型（"包含 A 或 B，但不要 C"），所以词表是 OR、维度之间是 AND；`排除优先` 让"看全部但躲开噪声"成为一条最短路径——加一个排除词就够，不必先把关键词收窄。

### 3.3 唯一判定点

沿用既有约定：**判定只在 `TrafficFilter::Matcher::accepts(record)` 一处实现**。`FilterBar` 只做条件收集，一行匹配逻辑都不写；测试与低频场景用一次性入口 `TrafficFilter::accepts(record, options, format)`（内部就是临时构造一个 `Matcher` 再调用，同一份实现）。

`Matcher` 在**条件变更时构造一次**（`updateFilter()`），构造期把该预编译的都编译掉，热路径只做判定：

1. **词表预编译**：`keywords` / `excludes` 的每一项在构造期变成 `TextCondition`——正则模式下 `QRegularExpression` 只编译一次，热路径只 `match()`。**非法正则的那条条件直接丢弃**（条件条标红提示），而不是退化成字面串匹配：退化的方向必须是"不过滤"，宁可多显示，也绝不因为写错一个括号把整屏数据静默吞掉。
   - 坑：默认构造的 `QRegularExpression` 是**有效且匹配一切**的，所以"这条是不是正则"必须用显式的 `bool m_regex` 记住，不能拿 `pattern.isValid()` 当判据（踩过一次：所有字面条件静默退化成匹配一切）。
2. **候选文本按"便宜 → 昂贵"排序 + 逐项短路**：对端地址、端点名、状态文本、详情、当前格式渲染文本、UTF-8 渲染文本、紧凑 HEX、带空格 HEX；后两项最贵，而只要前面的便宜项命中就直接返回，**多数消息上两条 HEX 串根本不会被构造**（现状 `accepts` 无条件构造两次 HEX，是既有的可优化点）。
3. **排除优先**：`excludes` 先判，命中即刻否决，再判 `keywords`。

这三个约束合成一句话：**判定成本与"条件数量"线性，与"文档行数"完全无关**——条件变更时才付一次编译成本，之后每条消息只走一遍短路比较。

## 4. 过滤与"搜索"的关系（已确认：合并）

搜索框升级为过滤的一部分，不再有第二套语义：

- 搜索框 = `keywords` 的快捷输入（空格 / 换行分隔多个词，全部 OR）；
- 过滤条里编辑 `keywords` 时，其词 chip 与输入框文本双向同步（同一份数据的两种视图，见 §7.2）；
- 保留独立输入框的原因是**高频快捷键位**：`Ctrl+F` 聚焦、回车即刻收流，不必进浮层。

## 5. 生效时机（关键决策）

| 方案                      | 行为                            | 成本                                                                        | 数据源                          | 结论                                                           |
| ----------------------- | ----------------------------- | ------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------ |
| **A. 仅新行**（现状语义）        | 改条件只影响之后到达的行                  | 0                                                                         | —                            | **F1 落地**：零新增路径，与"数据性能优先"零冲突；落差用计数与空态文案补 |
| **B. 新行 + 显式回溯重建**（F2）   | 过滤条上点 `重建视图`：清空视图 → 从模型重放命中项 | 清空是一次整块释放；重放 ≤ 2 万条 ≈ 60–120 ms（与文本历史长度无关，只与模型预算有关）                       | `TrafficModel`（2 万条 / 4 MiB） | 语义诚实、实现零新路径（复用 `appendMessages`），代价是**只回溯模型保留范围**，必须在 UI 上写明。**F2** |
| C. 全量回溯                 | 理想语义                          | 需要把结构化历史提升到与文本同级：100 万行 × 每条 Message 元数据（时间、来源、三个 QUuid、两个 QString）≈ GB 级 | 新增 second store              | 与"数据性能优先"直接冲突，否决                                             |

**决策：F1 采用方案 A（仅新行生效）；方案 B 的显式回溯重建划归 F2。**

理由：重建视图不是"多一个按钮"，它要改行号语义（重建后行号按结果连续重排 ⇒ `TrafficTextView::appendMessages` 要新增起始行号参数），并要把"只回溯模型保留范围"这件事在 UI 上讲清楚——这是一处独立的语义改动，不该和"条件收集 + 持久化"捆在一起发布。F1 先把条件与落盘做对，把"改完条件看不到结果"的落差用**两个诚实的反馈**补上：

- 状态栏摘要给出被挡下的条数：`共 N 条 · 过滤掉 M 条`（`m_filteredOut` 累加，O(1)）；
- 空态文案随过滤变化："当前过滤条件下没有匹配记录"，而不是"等待接收数据"——用户立刻知道是条件挡住了，而不是掉数据。

F2 落地方案 B 时要显式化的四件事（先记在这里，免得到时候重新推一遍）：

- 单行条上没有位置放常驻说明，范围写进 `重建视图` 的 tooltip："仅回溯最近 2 万条 / 4 MiB 内的记录，约 0.1 秒"；
- 重建后状态栏摘要播报："已重建视图 · 显示 N 条（模型保留范围内匹配）· 更早记录已清理"；
- 重建后行号按重建结果连续重排，摘要里注明"行号为重建后序号"；
- 需要更长历史的用户有明确出口：开启"记录到文件"（全量落盘，不受过滤影响）。

## 6. 性能预算与实现要点

- 每条消息判定：条件数 × 短路；典型 < 1 µs。**必须**保证：
  - 正则表达式在条件变更时用 `QRegularExpression` 预编译一次，热路径只 `match()`；
  - HEX 串**惰性构造**——只有存在"内容按 HEX 匹配"的条件时才把 `raw` 转成 HEX（现状 `accepts` 无条件构造两次 HEX 串，是既有的可优化点）；
  - 被禁用（未勾选）的条件不参与判定；
  - 长度条件是整数比较，不构造字符串。
- 明确不做：按行扫描文档、全表高亮、每条消息重建视图、为过滤复制一份原始字节。
- 命中高亮（F2）：只对**新追加的行**做，代价 O(命中数)；不对历史全表重刷。
- 计数：新增 `m_filteredOut`（被条件挡下的条数），状态栏摘要变为"共 N 条 · 过滤掉 M 条"，同时把"过滤生效中"体现在状态栏（避免用户以为掉数据）。
- perf 基准新增场景（**F2**）：`--filter 5`（5 个条件全开）下的净工作耗时，门槛沿用 < 10 ms/拍。F1 的判定路径已按上面的短路口径实现（条件数线性、与行数无关），补基准与 F2 的新条件维度一起做。

## 7. 交互设计

### 7.1 形态：两行头（顶栏 + 可折叠过滤条）

过滤条不占独立的一"块"，它是**监视区头的第二行**，与顶栏同处一个头块（行距 6px）：纵向成本就是一行控件的高度。默认展开，由顶栏的 `过滤` 按钮折叠——**折叠只隐藏第二行，条件照常生效**。

```text
┌ 监视区 ───────────────────────────────────────────────────────────────────────────┐
│ [A][B] [UTF-8 ▼] [⚙ 过滤 · 3 ▾]            [⚙显示设置] [导出] [↓滚动到底] [清空]   │ ← 顶栏
├──────────────────────────────────────────────────────────────────────────────────┤
│ 🔍关键词[ 心跳 0D0A ▏](心跳 ✕)(0D0A ✕)│⊖排除[ AA 55 ▏]│ ↓ ↑ ⓘ ⚠ ⊘ │⚙更多 (1)▾│ ⊘ │ ← 过滤条
├──────────────────────────────────────────────────────────────────────────────────┤
│ 1  14:30:01.201 [4 B] RX: 01 02 03 04                                            │ ← 数据区
└──────────────────────────────────────────────────────────────────────────────────┘
```

折叠后只剩顶栏一行（数据区上移），**按钮上的计数仍在报警**：

```text
│ [A][B] [UTF-8 ▼] [⚙ 过滤 · 3 ▸]            [⚙显示设置] [导出] [↓滚动到底] [清空]   │
```

五条形态约束：

- **恒为一行**：与顶栏那一行等高（内联控件走同一套 18px 最小高度 / 4px 内边距规格，与端点行同一约定），不随窗口宽度、也不随条件数量变化；数据区不会被它挤动。
- **宽度铺满**：关键词输入框是唯一弹性项，吸收全部剩余宽度，其余元素按自身 `sizeHint` 紧凑排在右侧；**永不换行、永不出现横向滚动条**。
- **可折叠但不失效**：`过滤` 是可勾选按钮（勾选 = 展开），文字恒带生效条件数；折叠用 `▸`、展开用 `▾`。条子收起来时，"当前在过滤"这件事仍然看得见——这是"过滤 · N"这个计数的唯一用途。
- **按钮一律带 Material 字形**（用户钦定）：字形取自 `@mdi/svg 7.4.47`，与既有 `cog.svg` / `arrow-down.svg` 同源、同一套 16px 尺寸。
- **零新增自绘**：元素只用 QSS 已覆盖的 `QPushButton` / `QLineEdit` / `QMenu`，不新增自绘控件、不写死像素。

**关于原顶栏搜索框**（修订已确认决策 #3 的形态）：关键词就是过滤条的第一格，顶栏不再重复放一个搜索框——搜索框原本占据顶栏唯一的弹性位置，把它连同"关键词"语义一起下移到过滤条，等于用同一行高度换到一整行的可用宽度；腾出的位置给 `过滤` 折叠按钮。`Ctrl+F` 行为不变（必要时先展开再聚焦），`Ctrl+Shift+F` 展开/收起整条。

### 7.2 条件条的解剖（从左到右）

| 组  | 元素                     | 字形（Material）                  | 文字         | 宽度策略        | 说明                                 |
| -- | ---------------------- | ----------------------------- | ---------- | ----------- | ---------------------------------- |
| 折叠 | `过滤 · N ▾`             | `filter-variant`              | 有          | 定宽（顶栏）      | 顶栏唯一入口；勾选 = 展开，N = 生效条件数           |
| 内容 | 关键词输入                  | `magnify`（前导）                 | placeholder | **弹性（吸收余量）** | 空格分隔多词、任一命中（OR）；`Ctrl+F` 的落点       |
| 内容 | 关键词 chip               | 无（`✕` 为文字字形）                  | 词本身 + `✕`  | 按内容，最多 3 个  | 与输入框文本是**同一份数据**的两种视图：点 chip 等于删掉该词 |
| 内容 | 排除词输入                  | `minus-circle-outline`（前导）    | placeholder | 定宽，最小 8em   | 命中即隐藏（黑名单），优先于关键词                  |
| 条件 | RX                     | `arrow-down-bold`             | **无**      | 定宽          | 显示接收                               |
| 条件 | TX                     | `arrow-up-bold`               | **无**      | 定宽          | 显示发送                               |
| 条件 | 状态                     | `information-outline`         | **无**      | 定宽          | 状态迁移（端口打开 / 关闭 / 重连）                |
| 条件 | 警告                     | `alert-outline`               | **无**      | 定宽          | 警告日志                               |
| 条件 | 错误                     | `alert-circle-outline`        | **无**      | 定宽          | 错误日志                               |
| 条件 | `更多 (N) ▾`             | `tune`                        | 有          | 定宽          | 低频维度与匹配选项收进浮层；勾选不关闭，浮层不占布局高度       |
| 动作 | 重置                     | `filter-off`                  | **无**      | 定宽          | 清空全部条件，回到不过滤；无条件时置灰                |

**字形与文字的取舍**：箭头、信息、警示、错误这四个字形自身即语义，配上文字每个要多占 3~4 倍宽度，所以方向与事件按钮**只给字形 + tooltip**；`更多` / `重置` / `过滤` 这类动作用途不唯一，必须留文字。判据一句话：**字形是否唯一指向该动作**。

**勾选按钮的字形要手动换色**：`QPushButton` 的图标状态位跟的是"按下"而不是"勾选"，勾选态必须按 `toggled` 显式换成与 QSS 选中文字同色的深琥珀（`tintedIcon()`），否则琥珀底上会出现灰字。

`更多` 浮层内容（浮层纵向展开、浮在数据区之上，高度不受主条约束；F1 只有匹配选项，F2 的帧类型 / 长度 / 对端 / 来源直接并进这一个浮层）：

```text
更多
├ 帧类型   ☑ 完整帧   ☐ 流片段   ☐ 数据报      ← F2
├ 长度     [     ] ~ [     ] 字节            ← F2
├ 对端     [ 192.168.1.            ]        ← F2
├ 来源     ☑自动  ☑手动  ☑定时  ☑转发  ☐示例  ← F2
└ 匹配     ☐ 区分大小写    ☐ 正则表达式        ← F1 已实现
```

浮层里的每一项与主条上的按钮**共用同一份条件**——浮层只是同一份状态的另一种呈现，不产生第二套布尔值。

**单一状态源**：`RX / TX / 状态 / 警告 / 错误` 五个开关只有一份状态，就住在过滤条上（已从"显示设置"菜单迁出）。原"显示错误日志"这一个布尔拆成 `状态 / 警告 / 错误` 三个独立开关，`TrafficFilter::Options` 里的 `events` 由三者取代。控件 objectName：`filterRx` / `filterTx` / `filterState` / `filterWarning` / `filterError`。

### 7.3 宽度预算与折叠规则

| 可用宽度 | 形态                                              |
| ---- | ----------------------------------------------- |
| 宽    | 全部摊开：关键词（吸收余量）+ 排除 + 5 个方向按钮 + 更多 + 重置         |
| 窄    | 关键词输入压到最小宽度；chip 只显示前 3 个，其余用一个 `+N` 收口         |
| 更窄    | 用户自行折叠整条（`过滤 · N ▸`），条件照常生效                    |

**不按宽度动态把按钮搬进浮层**：那需要两套排布加一次判据，收益只有几十像素；把"更窄"交给用户手上的折叠按钮更直接、更可预期，也让布局只有一种形态可测。硬规则不变：**任何宽度下都保持单行**——`QHBoxLayout` 只会压缩，永不换行、永不出现横向滚动条。

### 7.4 与"显示设置"的分工

| 面板   | 管什么        | 例子                                 |
| ---- | ---------- | ---------------------------------- |
| 显示设置 | **每行长什么样** | 行号、时间戳、方向、长度、HEX 对照、纯数据、自动换行、记录到文件 |
| 过滤   | **哪些行进来**  | 关键词、排除词、方向、端点、事件类型、长度、对端、帧类型       |

按这条线重新归位：**`RX` / `TX` / `状态` / `警告` / `错误` 从"显示设置"菜单迁入过滤条**（它们管的是"哪些行进来"，原本放错了地方），显示设置菜单随后只剩行内容开关与"记录到文件"，反而更短。`A` / `B` 端点开关仍留在顶栏左端（高频、且属于范围而非条件），过滤条不重复它们。

两者都在到达时生效，都不回溯（F1 没有回溯入口，见 §5）。

### 7.5 反馈

- 条数摘要：`共 12,043 条 · 过滤掉 8,912 条`（进主窗口状态栏，不占面板空间）。过滤是"静默少显示"，必须有一个能证明"数据没丢、只是被挡住"的数字。
- **顶栏折叠按钮承载计数**：文字恒为 `过滤 · N ▾`（N = 生效条件数），收起时变 `过滤 · N ▸`；N 为 0 时省掉数字。这是这个计数唯一的用途——**条子收起来时，"当前在过滤"这件事仍然看得见**。浮层里的 `更多 (N)` 另计浮层内生效的条件数，两个 N 各管自己那一层，不合并。
- 条件本身显示为可删除条目（chip），不用弹窗确认；点 chip 等于从输入框文本里删掉那个词，chip 只是同一份文本的视图。
- 正则非法时输入框红框 + 提示，且**该条件不参与判定**（退化为不过滤，绝不静默吞掉全部数据）。
- 空态提示随之变化："当前过滤条件下没有匹配记录"，而不是"等待接收数据"。
